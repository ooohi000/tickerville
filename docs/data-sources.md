# 데이터 소스 조사 (2026-10-19)

## ✅ 최종 결정
**공개 사이트는 무료·공개 가능 데이터만 쓴다. 월 $0.**
| 용도 | 소스 |
|---|---|
| 재무제표, 매출(TTM), 공시 활동, 기업 기본 정보 | SEC EDGAR |
| 시장 날씨 지수 | FRED 금융스트레스 지수(STLFSI4, 연준 자체 지표 — 출처 표기 조건) |
| 매크로 (금리·금리차·유가·천연가스·달러 가치) | FRED 공공 시리즈 |
| 원/달러 | 한국수출입은행 |
| 주가·시총·거래량 | **안 씀.** 필요하면 본인만 보는 개인 모드에서만 |

유료 공개 라이선스는 사이드 프로젝트 기준으로 너무 비싸서 제외 (아래 조사 내용). FMP는 쓰지 않는다.
SEC는 sec.gov 정보가 공개 정보이며 허락 없이 복사·재배포할 수 있다고 안내한다(출처 표기 요청). OpenInsider 같은 사이트도 SEC 공시를 모아 보여준다.

> 법률 자문 아님 — 공개 표시 권한은 각 제공처에 **서면으로** 확인하는 게 안전하다.

## 한 줄 결론
- **재무제표·금리·환율·유가·천연가스는 무료로 공개 가능** (SEC, FRED의 공공 데이터, 한국수출입은행)
- **주가·시총·거래량, 금·은 일별, VIX, CNN 공포·탐욕은 "공개 사이트에 보여주는 것"에 라이선스가 걸린다**
- 거의 모든 주가 API의 개인 요금제는 "본인만 보는 용도"라서, 방문자가 보는 순간 사업자/표시 라이선스가 필요하다

## 2. 재무제표 — SEC EDGAR ✅ 무료
- API 키 없음, 무료. `companyfacts`(기업별 전체 XBRL 항목), `submissions`(공시 이력·주소) 등
- 공시 후 1분 안팎 반영, 대량용 zip은 매일 새벽 3시(미 동부) 갱신
- 규칙: **초당 10회 이하**, 요청 헤더에 `User-Agent: 앱이름 연락처이메일` 필수
- 할 일: 기업마다 다른 XBRL 항목명을 매출·영업이익 등으로 정규화하는 작업

## 추가 확인 (2026-10-19 오후)
- **FMP 공개 표시 = Enterprise 요금제만.** 가격 비공개(영업 문의). 개인 요금제(연간결제 월 $19/$49/$99)로는 공개 불가 → 공개용으론 부적합
- **재무제표는 SEC를 원본으로.** 무료·공개 가능·원본이라 날짜가 정확하다. 정리된 API는 회계연도 기준을 섞어 쓰면 날짜가 어긋나 보일 수 있다
  - SEC 함정: `companyfacts`의 `fy`·`fp`는 **그 값이 실린 공시의** 회계연도·분기다. 10-K에 같이 실린 전년도 비교값도 같은 `fy`를 단다 → 기간은 반드시 `start`·`end` 날짜로 판정하고, 같은 기간이 여러 공시에 나오면 `filed`가 최신인 값(정정 반영)을 쓴다
- 바뀐 추천: 재무제표·발행주식수 = SEC, 주가·거래량 = 공개 표시 가능한 저가 제공처(Marketstack 확인), FMP는 쓰지 않거나 개발 중 교차 검증용

## SEC 실제 데이터 확인 (2026-10-19, 7개 기업 직접 수집)
대상: AAPL·NVDA·JPM·KO·PLTR·TSLA·AMZN. 접속 OK (User-Agent에 연락처, 요청 간 0.3초).

### 기업마다 다른 것 → "개념 후보 목록 + 업종 규칙"으로 정규화
| 항목 | 관찰 |
|---|---|
| 매출 | AAPL·PLTR·AMZN = `RevenueFromContractWithCustomerExcludingAssessedTax`, KO = `Revenues`, **NVDA는 2022년에 이름을 바꿈**(→ `Revenues`), **JPM(은행) = `RevenuesNetOfInterestExpense`** |
| 영업이익 | 대부분 `OperatingIncomeLoss`, **은행(JPM)은 없음** → 영업이익률 `null` |
| 설비투자 | `PaymentsToAcquirePropertyPlantAndEquipment` 또는 `PaymentsToAcquireProductiveAssets`(NVDA·AMZN), 은행은 없음 |
| 순이익·총자산·영업현금흐름 | 7개 모두 `NetIncomeLoss`·`Assets`·`NetCashProvidedByUsedInOperatingActivities` |
| 발행주식수 | `dei:EntityCommonStockSharesOutstanding` 분기마다 갱신. **PLTR은 없음**(주식 종류가 여러 개) |
| 공시상 시총 | `dei:EntityPublicFloat` 7개 모두 있음. 기준일이 **2025년 3~7월**이라 1년 이상 묵음 (예상대로) |

→ 규칙: 기업마다 고정 개념을 정하지 말고, **기간마다 후보 목록을 우선순위대로 찾아 값이 있는 것**을 쓴다. 은행은 별도 후보 목록.

### 기간 함정 (확인됨)
- **10-Q 한 건에 3개월 값과 누적 값이 같이 있다**: AAPL 3분기 10-Q에 90일(3개월)·272일(9개월 누적) 값이 전년·당해 각각 → **기간 길이(약 90일)로 분기 값을 고른다**
- **10-K 한 건에 3개 연도가 전부 `fy=2025, fp=FY`로 들어 있다** → `fy`·`fp` 믿지 말고 `start`·`end`로 판정
- 4분기 값은 따로 없다 → 연간 − (1~3분기)
- 같은 기간이 여러 공시에 반복 등장 (한 기간이 4번) → `filed` 최신 값
- **KO는 최신 분기(2026-06) 매출이 companyfacts에 아직 없음** (마지막 2026-04-03) → 기업마다 "데이터 기준일"을 따로 저장하고 화면에 표시

### submissions에서 바로 얻는 것
- 회계연도 마감(AAPL 0926, NVDA 0131, 나머지 1231), SIC 업종, 거래소, **본사 주소**
- **PLTR 본사가 플로리다 Aventura로 나옴** (목데이터의 덴버와 다름) → 본사 좌표는 SEC 주소로 갱신하는 게 맞다
- 최근 30일: AAPL Form 4 14건, NVDA 4건, PLTR 7건, JPM 8-K 2건·Form 4 5건, TSLA 8-K 2건, KO 0건 → 공시 열기에 실제로 차이가 난다
- JPM은 구조화 채권 공시 때문에 최근 목록이 2만 건 이상(파일 4.6MB) → 공시 집계는 폼 종류로 거르고, 큰 응답에 대비

### 스키마에 반영할 것
- `financial_fact`: 필요한 개념만 원본 행으로 저장 (개념, 단위, start, end, 값, 공시번호, filed, form)
- `financial_period`: 정규화 결과 (기업, 기간 종류 Q/FY, 기간 시작·끝, 매출·순이익…) — 계산은 순수 클래스
- `company`: SEC 기본 정보 + `dataAsOf`(재무 데이터 기준일)

## 데이터 쌓기 원칙 (2026-10-19 결정)
다시 받을 수 있는 데이터(SEC 재무·공시 원본)보다 **그날 안 쌓으면 사라지는 데이터**를 우선 쌓는다.

| 쌓을 것 | 왜 | 테이블(예정) | 언제 |
|---|---|---|---|
| 매일 지도 지표 (매출 TTM·순이익·자산·성장률·공시 건수…) | `company_snapshot`은 덮어쓰기라 어제 값이 사라짐. 타임랩스·변화 알림의 재료 | `company_metric_daily` (기업·날짜당 한 줄 + `calc_version`) | SEC 수집기 (최신값과 같은 트랜잭션) |
| 실적 발표일 이벤트 | 예상 → 확정(언제 발표됐나) → 실제 발표(8-K 2.02). 확정 시점 기록은 나중에 못 만든다 | `earnings_event` (예상일·확정일·확정 기록 시각·실제 공시·장전/장후) | SEC 수집기 + 관리자 입력 |
| 시장 날씨 계산 원본 | 공식을 바꿔도 과거를 다시 계산 | `market_weather.stress_index` ✅ 이미 저장 | FRED 수집기 |
| 방문자 행동 (익명 일별 집계) | "한국 투자자가 많이 보는 미국 기업" — 우리만의 데이터 | `company_view_daily` (기업·날짜·클릭 수, 개인정보 없음) | 프론트 API 연결(4단계) |

- 용량: 기업 500개 × 365일 ≈ 18만 줄/년. 파티션은 몇 년 뒤에 검토
- 정리 규칙을 바꾸면 `calc_version`을 올린다 (같은 날짜라도 버전이 다르면 비교하지 않는다)

## 수집기에서 확인된 것 (2026-10-19)
- **위임장(DEF 14A)도 재무 값을 반올림해서 다시 태그한다** (JPM 2024 순이익 58,471 → 58,500백만) → 정기 보고서(10-K·10-Q) 값만 쓴다
- **정정이 공시마다 따로 반영된다** (JPM 2019 매출: 1분기 단독 값은 그대로, 누적 값만 정정) → 4분기 = 연간 − (1~3분기 합)으로 네 분기 합을 연간에 맞춘다
- **SEC companyfacts 가 공시보다 늦을 수 있다** (KO: 2026-07-03 분기 10-Q 를 7/29 제출했는데 숫자 없음) → 품질 검사 `FACTS_BEHIND_FILINGS`로 표시, 다음 수집 때 자동 반영
- 실적 발표 장전·장후는 **8-K 접수 시각** 기준이라 실제 보도자료 시각과 다를 수 있다 (JPM 은 장 전 보도자료, 8-K 접수는 오전 10시 반)
